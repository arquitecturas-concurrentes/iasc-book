== Introducción a OTP

OTP (Open Telecom Platform) es el conjunto de bibliotecas, herramientas y principios de diseño que acompaña a Erlang/BEAM y que también se usa desde Elixir. No es otro lenguaje ni un único framework: ofrece comportamientos y convenciones para implementar procesos, componer aplicaciones y definir qué hacer cuando un proceso termina de forma inesperada. Por ejemplo, al usar `GenServer` se escriben los callbacks que describen el comportamiento del servidor y OTP se ocupa del bucle de recepción y de la interacción estándar con ese proceso.

El modelo de actores ayuda a entender la idea central: procesos aislados que colaboran mediante mensajes. OTP no cambia esa forma de comunicación; ofrece piezas para no tener que resolver desde cero tareas comunes como mantener estado (`Agent`), atender solicitudes (`GenServer`), ejecutar un trabajo acotado (`Task`), iniciar procesos (`Application`), supervisar su ciclo de vida (`Supervisor`) o encontrarlos por un nombre (`Registry`). Estas piezas tienen funciones distintas y suelen combinarse: una aplicación inicia un árbol de supervisión, el supervisor inicia los procesos de trabajo y un registro permite localizarlos cuando no se quiere depender de conocer directamente su PID.

== Una aplicación OTP como árbol de procesos

La arquitectura típica de una aplicación OTP se puede leer como una cadena de responsabilidades:

. *Application* es el punto de entrada del ciclo de vida de la aplicación.
. La aplicación inicia un supervisor raíz.
. El supervisor inicia procesos hijos, como servidores, agentes, tareas o incluso otros supervisores.
. Los procesos de trabajo implementan la lógica y se comunican mediante mensajes; si un proceso termina, el supervisor aplica la política de reinicio declarada para ese hijo.

Esta estructura se llama *árbol de supervisión*. Es importante porque el modo de iniciar un proceso queda declarado junto con el resto de la arquitectura, en vez de dispersarse en llamadas manuales por el código. Los comportamientos de OTP definen contratos de callbacks: el programador escribe las funciones que describen la lógica de la aplicación y el runtime ejecuta el ciclo de vida común alrededor de ellas. Este diseño y sus principios se explican en la guía de https://www.erlang.org/doc/system/design_principles.html[principios de diseño de OTP] <<OTPDesignPrinciples>>.

Supervisar no significa que OTP pueda corregir cualquier error ni que los procesos no fallen. El supervisor decide cómo continuar cuando un hijo termina; la aplicación debe definir qué fallas ameritan reinicio, qué estado puede reconstruirse y qué efectos externos podrían repetirse. Reiniciar un proceso no revierte operaciones ya realizadas ni vuelve persistente su estado en memoria.

== GenServer

`GenServer` es un comportamiento de OTP para implementar un proceso servidor. El módulo define su estado inicial y callbacks que procesan solicitudes; OTP implementa el ciclo de vida y el bucle que recibe mensajes. Por convención, se separa la API pública del módulo —las funciones que usan sus clientes— de los callbacks que ejecuta el proceso servidor.

La llamada subyacente entre procesos sigue siendo por mensajes. `GenServer.call/3` implementa un intercambio de solicitud y respuesta: el cliente espera la respuesta o un timeout, mientras el servidor procesa la solicitud en `handle_call/3`. En cambio, `GenServer.cast/2` envía una solicitud asincrónica sin esperar una respuesta; el cliente no obtiene confirmación de que la operación se haya procesado.

Por eso, se elige `call` cuando el cliente necesita una respuesta para continuar; `cast` sirve cuando no necesita respuesta inmediata y el protocolo puede tolerar que el emisor no sepa si el servidor procesó el mensaje. Un timeout de `call` indica que no se recibió la respuesta a tiempo, pero no demuestra que la operación no se haya ejecutado: el servidor podría haberla procesado y la respuesta haberse demorado. Las llamadas y los casts se procesan en el orden en que llegan al servidor, pero no establecen un orden global respecto de mensajes enviados por otros procesos.

* `handle_call/3` devuelve una tupla como `{:reply, respuesta, nuevo_estado}`.
* `handle_cast/2` devuelve, por ejemplo, `{:noreply, nuevo_estado}`.
* `handle_info/2` procesa otros mensajes recibidos por el proceso, por ejemplo los enviados con `send/2`.

En cada callback se devuelve el estado con el que continuará el servidor. Como un proceso maneja sus callbacks de forma secuencial, el estado no se modifica directamente desde el cliente.

=== Ejemplo: contador de likes

Este ejemplo sigue el `Post` que usamos en la clase. El servidor mantiene el número de likes; los clientes pueden incrementarlo sin esperar una respuesta y consultar el valor mediante una llamada:

[source,elixir]
----
defmodule Post do
  use GenServer

  def start_link(initial_likes) do
    GenServer.start_link(__MODULE__, initial_likes, name: __MODULE__)
  end

  @impl true
  def init(initial_likes), do: {:ok, initial_likes}

  def like, do: GenServer.cast(__MODULE__, :like)
  def likes, do: GenServer.call(__MODULE__, :get)

  @impl true
  def handle_cast(:like, likes) do
    {:noreply, likes + 1}
  end

  @impl true
  def handle_call(:get, _from, likes) do
    {:reply, likes, likes}
  end
end
----

`start_link/1` inicia el proceso vinculado al proceso que lo inicia y lo registra localmente con el nombre `Post`. `init/1` establece el estado inicial. `like/0` envía un cast y retorna sin esperar que el contador se actualice; `likes/0` hace un call y devuelve el valor procesado por el servidor. En una aplicación, normalmente el proceso se inicia como hijo de un supervisor.

Más información: https://hexdocs.pm/elixir/GenServer.html[documentación de GenServer] y https://elixir-lang.org/getting-started/mix-otp/genserver.html[guía de GenServer].

== Agent

`Agent` es una abstracción más directa para un proceso cuyo propósito principal es mantener estado. El estado permanece encapsulado en el proceso y se consulta o actualiza mediante funciones como `Agent.get/3` y `Agent.update/3`. Conviene cuando la lógica de transición es sencilla; si el proceso necesita un protocolo más elaborado, callbacks específicos o manejar varios tipos de mensajes, `GenServer` suele ser más apropiado.

Este ejemplo modela un mapa en memoria y está basado en el `KV.Agent` de la clase:

[source,elixir]
----
defmodule KV.Agent do
  def start_link do
    Agent.start_link(fn -> %{} end)
  end

  def get(agent, key) do
    Agent.get(agent, &Map.get(&1, key))
  end

  def put(agent, key, value) do
    Agent.update(agent, &Map.put(&1, key, value))
  end
end

{:ok, pid} = KV.Agent.start_link()
KV.Agent.put(pid, :hello, :world)
KV.Agent.get(pid, :hello)
# :world
----

El estado de un `Agent` vive en memoria: no se persiste automáticamente en disco. Si el proceso termina y se reinicia, vuelve al estado que indique su inicialización, salvo que la aplicación recupere el estado desde otro lugar. Un Agent también puede ser iniciado y supervisado como hijo de un supervisor.

Más información: https://hexdocs.pm/elixir/Agent.html[documentación de Agent].

== Task

`Task` representa trabajo que se ejecuta concurrentemente y tiene un principio y un fin; no es una abstracción para almacenar estado de largo plazo. Para obtener un resultado, `Task.async/1` inicia una tarea vinculada al proceso que la crea y devuelve una referencia; `Task.await/2` espera su respuesta:

[source,elixir]
----
task = Task.async(fn -> Enum.sum(1..10) end)
Task.await(task)
# 55
----

La espera de `await` ocurre en el proceso cliente; la tarea corre en otro proceso. Si la tarea falla, `await` vuelve a levantar la excepción en quien espera. `Task.start/1` inicia trabajo asincrónico sin recolectar un resultado mediante `await`. Cuando una tarea debe formar parte del ciclo de vida de una aplicación, `Task.start_link/1` o una especificación de hijo de `Task` permiten vincularla al proceso iniciador o iniciarla bajo supervisión, según el caso. Las tareas vinculadas propagan señales de salida de acuerdo con las reglas de links; para aislar y controlar fallas en aplicaciones, se debe elegir conscientemente la estrategia de inicio y supervisión.

En el proyecto de la clase, `IASC.WriteHaiku` usa una tarea para escribir o leer un archivo. Es un trabajo finito: una vez terminada la operación, el proceso de la tarea termina. El ejemplo puede consultarse en el https://github.com/arquitecturas-concurrentes/iasc-actors-intro-elixir/blob/master/intro_actors/lib/intro_task.ex[código de Task].

Más información: https://hexdocs.pm/elixir/Task.html[documentación de Task].

== Application, Registry y ETS

=== Application

En Elixir, una *aplicación OTP* es una unidad de software con configuración, dependencias y un ciclo de vida definido. No debe confundirse con un proceso: una aplicación puede iniciar y coordinar muchos procesos.

El comportamiento `Application` proporciona el punto de entrada de ese ciclo de vida. Al arrancar la aplicación, OTP llama a `start/2` del módulo configurado para ella. Habitualmente, ese callback inicia y devuelve el supervisor raíz; el supervisor, a su vez, inicia los procesos que la aplicación necesita. Así, al iniciar una aplicación con Mix, no hace falta crear manualmente cada proceso desde la consola: el árbol de supervisión describe qué debe arrancar. Al detener la aplicación, OTP también coordina el cierre de esos procesos.

La configuración de Mix indica qué módulo implementa el callback de inicio y qué otras aplicaciones son dependencias. OTP inicia primero las dependencias y luego llama a `start/2`; al apagar, detiene la aplicación y sus procesos de forma coordinada. En proyectos reales, el árbol raíz suele incluir componentes compartidos por toda la aplicación, como un `Registry`, un `DynamicSupervisor` y servidores de larga duración. El callback de `Application` normalmente se limita a construir y arrancar ese árbol.

Una aplicación pequeña puede empezar con un módulo que implemente `Application` y un supervisor. Para que el ejemplo sea autocontenido, el supervisor inicia un `Agent` que mantiene un mapa en memoria:

[source,elixir]
----
defmodule MiApp.Application do
  use Application

  @impl true
  def start(_type, _args) do
    children = [
      {Agent, fn -> %{} end}
    ]

    Supervisor.start_link(children, strategy: :one_for_one, name: MiApp.Supervisor)
  end
end
----

En este ejemplo, `start/2` no crea directamente el proceso con `Agent.start_link/1`: declara una especificación de hijo para que el supervisor lo inicie y gestione. La aplicación y el supervisor cumplen roles distintos: `Application` conecta el arranque de la aplicación con su supervisor raíz; `Supervisor` administra los procesos hijos. En una aplicación real, un módulo propio puede envolver ese Agent y ofrecer una API con nombre para consultarlo.

Más información: https://hexdocs.pm/elixir/Application.html[documentación de Application] y https://elixir-lang.org/getting-started/mix-otp/supervisor-and-application.html[guía de aplicaciones y supervisores].

=== Registry

`Registry` asocia claves locales a procesos para que los clientes puedan encontrarlos sin guardar directamente sus PID. Las claves pueden ser `:unique` o `:duplicate`; la primera opción sirve para nombres de servidor y la segunda permite patrones como suscripciones. Un Registry no almacena el estado de negocio ni persiste sus entradas. En una aplicación suele iniciarse bajo supervisión y antes que los procesos que se registran en él.

Para una explicación detallada de `:via`, claves únicas y duplicadas, despacho, supervisión dinámica y comportamiento ante fallas, véase https://arquitecturas-concurrentes.github.io/iasc-book/registry_elixir[Registry en Elixir: nombres y localización de procesos].

=== ETS

ETS (Erlang Term Storage) ofrece tablas en memoria para almacenar y consultar datos desde procesos. A diferencia de `Agent`, que presenta una interfaz de proceso para leer o actualizar un estado, ETS ofrece operaciones directas sobre una tabla y permite distintos patrones de acceso concurrente. La tabla y sus datos siguen siendo volátiles: su ciclo de vida está asociado a quien la posee y no se persisten automáticamente en disco.

Más información: https://elixir-lang.org/getting-started/mix-otp/ets.html[guía de ETS].

== Supervisores

Un supervisor es un proceso OTP que inicia y supervisa procesos hijos de acuerdo con sus especificaciones. Los supervisores pueden organizarse en árboles: la aplicación inicia un supervisor raíz, que a su vez puede iniciar otros supervisores y procesos de trabajo. Así se declara cómo se inician, se detienen y se reinician los componentes cuando fallan.

Cada hijo tiene una especificación (child spec) que describe cómo iniciarlo y qué política de reinicio y apagado aplicar. La estrategia determina qué hijos reiniciar ante una falla. Por ejemplo, `:one_for_one` reinicia solo al hijo que falló; `:one_for_all` reinicia a todos los hijos del supervisor; y `:rest_for_one` reinicia al hijo fallido y a los que fueron iniciados después de él. El orden de los hijos, por lo tanto, importa en las dos últimas estrategias: al iniciar, se recorren en orden; al apagar, se detienen en orden inverso.

La política `:permanent` intenta reiniciar el hijo ante cualquier terminación, `:temporary` no lo reinicia y `:transient` lo reinicia solo si terminó por una razón anormal. Además, el supervisor limita la cantidad de reinicios dentro de una ventana de tiempo; si se supera el límite, el propio supervisor termina para que el fallo no genere un ciclo de reinicios ilimitado. Un `DynamicSupervisor` permite iniciar hijos dinámicamente después de que el supervisor ya está en marcha; para hijos conocidos al iniciar, se declaran especificaciones en el supervisor habitual.

La supervisión no restaura automáticamente el estado que tenía un proceso antes de terminar. Si se reinicia un `GenServer` o un `Agent`, este se inicializa de nuevo; si el estado debe sobrevivir a una falla, hay que persistirlo o reconstruirlo explícitamente. Por eso, la política de reinicio y la recuperación del estado son decisiones distintas.

Más información: https://hexdocs.pm/elixir/Supervisor.html[Supervisor] y https://hexdocs.pm/elixir/DynamicSupervisor.html[DynamicSupervisor].
