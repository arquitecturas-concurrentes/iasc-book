== Introducción a OTP

OTP (Open Telecom Platform) es el conjunto de bibliotecas, herramientas y principios de diseño que acompaña a Erlang/BEAM y que también se usa desde Elixir. No es otro lenguaje ni un único framework: ofrece comportamientos reutilizables para construir procesos, organizar su ciclo de vida y recuperarse ante fallas. En lugar de escribir a mano el bucle de recepción de cada proceso, se puede implementar un comportamiento estándar y dejar que OTP gestione ese bucle.

En esta clase nos enfocamos en tres abstracciones:

* `GenServer`, para procesos con estado y un protocolo de solicitudes;
* `Agent`, para mantener estado simple sin escribir callbacks propios;
* `Task`, para ejecutar trabajo acotado de manera concurrente.

Estas abstracciones no reemplazan el modelo de actores ni el paso de mensajes. Encapsulan patrones comunes sobre procesos BEAM. `Application`, `Supervisor` y `Registry` completan el contexto de cómo se inicia y organiza una aplicación real.

== GenServer

`GenServer` es un comportamiento de OTP para implementar un proceso servidor. El módulo define su estado inicial y callbacks que procesan solicitudes; OTP implementa el ciclo de vida y el bucle que recibe mensajes. Por convención, se separa la API pública del módulo —las funciones que usan sus clientes— de los callbacks que ejecuta el proceso servidor.

La llamada subyacente entre procesos sigue siendo por mensajes. `GenServer.call/3` implementa un intercambio de solicitud y respuesta: el cliente espera la respuesta o un timeout, mientras el servidor procesa la solicitud en `handle_call/3`. En cambio, `GenServer.cast/2` envía una solicitud asincrónica sin esperar una respuesta; el cliente no obtiene confirmación de que la operación se haya procesado.

* `handle_call/3` devuelve una tupla como `{:reply, respuesta, nuevo_estado}`.
* `handle_cast/2` devuelve, por ejemplo, `{:noreply, nuevo_estado}`.
* `handle_info/2` procesa otros mensajes recibidos por el proceso, por ejemplo los enviados con `send/2`.

En cada callback se devuelve el estado con el que continuará el servidor. Como un proceso maneja sus callbacks de forma secuencial, el estado no se modifica directamente desde el cliente.

=== Ejemplo: contador de likes

Este ejemplo sigue el `Post` que usamos en la clase. El servidor mantiene el número de likes; los clientes pueden incrementarlo sin esperar una respuesta y consultar el valor mediante una llamada:

[source,elixir]
----
defmodule Post do
  use GenServer

  def start_link(initial_likes) do
    GenServer.start_link(__MODULE__, initial_likes, name: __MODULE__)
  end

  @impl true
  def init(initial_likes), do: {:ok, initial_likes}

  def like, do: GenServer.cast(__MODULE__, :like)
  def likes, do: GenServer.call(__MODULE__, :get)

  @impl true
  def handle_cast(:like, likes) do
    {:noreply, likes + 1}
  end

  @impl true
  def handle_call(:get, _from, likes) do
    {:reply, likes, likes}
  end
end
----

`start_link/1` inicia el proceso vinculado al proceso que lo inicia y lo registra localmente con el nombre `Post`. `init/1` establece el estado inicial. `like/0` envía un cast y retorna sin esperar que el contador se actualice; `likes/0` hace un call y devuelve el valor procesado por el servidor. En una aplicación, normalmente el proceso se inicia como hijo de un supervisor.

Más información: https://hexdocs.pm/elixir/GenServer.html[documentación de GenServer] y https://elixir-lang.org/getting-started/mix-otp/genserver.html[guía de GenServer].

== Agent

`Agent` es una abstracción más directa para un proceso cuyo propósito principal es mantener estado. El estado permanece encapsulado en el proceso y se consulta o actualiza mediante funciones como `Agent.get/3` y `Agent.update/3`. Conviene cuando la lógica de transición es sencilla; si el proceso necesita un protocolo más elaborado, callbacks específicos o manejar varios tipos de mensajes, `GenServer` suele ser más apropiado.

Este ejemplo modela un mapa en memoria y está basado en el `KV.Agent` de la clase:

[source,elixir]
----
defmodule KV.Agent do
  def start_link do
    Agent.start_link(fn -> %{} end)
  end

  def get(agent, key) do
    Agent.get(agent, &Map.get(&1, key))
  end

  def put(agent, key, value) do
    Agent.update(agent, &Map.put(&1, key, value))
  end
end

{:ok, pid} = KV.Agent.start_link()
KV.Agent.put(pid, :hello, :world)
KV.Agent.get(pid, :hello)
# :world
----

El estado de un `Agent` vive en memoria: no se persiste automáticamente en disco. Si el proceso termina y se reinicia, vuelve al estado que indique su inicialización, salvo que la aplicación recupere el estado desde otro lugar. Un Agent también puede ser iniciado y supervisado como hijo de un supervisor.

Más información: https://hexdocs.pm/elixir/Agent.html[documentación de Agent].

== Task

`Task` representa trabajo que se ejecuta concurrentemente y tiene un principio y un fin; no es una abstracción para almacenar estado de largo plazo. Para obtener un resultado, `Task.async/1` inicia la tarea y `Task.await/2` espera su respuesta:

[source,elixir]
----
task = Task.async(fn -> Enum.sum(1..10) end)
Task.await(task)
# 55
----

La espera de `await` ocurre en el proceso cliente; la tarea corre en otro proceso. `Task.start/1` inicia trabajo asincrónico sin recolectar un resultado mediante `await`. Cuando una tarea debe formar parte del ciclo de vida de una aplicación, `Task.start_link/1` o una especificación de hijo de `Task` permiten vincularla al proceso iniciador o iniciarla bajo supervisión, según el caso. Las tareas vinculadas propagan señales de salida de acuerdo con las reglas de links; para aislar y controlar fallas en aplicaciones, se debe elegir conscientemente la estrategia de inicio y supervisión.

En el proyecto de la clase, `IASC.WriteHaiku` usa una tarea para escribir o leer un archivo. Es un trabajo finito: una vez terminada la operación, el proceso de la tarea termina. El ejemplo puede consultarse en el https://github.com/arquitecturas-concurrentes/iasc-actors-intro-elixir/blob/master/intro_actors/lib/intro_task.ex[código de Task].

Más información: https://hexdocs.pm/elixir/Task.html[documentación de Task].

== Application, Registry y ETS

`Application` define el punto de entrada para iniciar una aplicación y, habitualmente, su árbol de supervisión. El callback `start/2` de la aplicación inicia el supervisor raíz y sus procesos hijos.

`Registry` permite asociar nombres o claves con procesos y despachar mensajes a esos procesos. No es un almacenamiento persistente de datos de negocio; su uso habitual es localizar procesos dinámicos o implementar patrones de registro y publicación/suscripción.

ETS (Erlang Term Storage) ofrece tablas en memoria para almacenar y consultar datos desde procesos. Su modelo de acceso y ciclo de vida difieren de los de un `Agent`; elegir entre ambos depende de cómo se comparte y consulta el estado.

Más información: https://hexdocs.pm/elixir/Application.html[Application], https://hexdocs.pm/elixir/Registry.html[Registry] y https://elixir-lang.org/getting-started/mix-otp/ets.html[ETS].

== Supervisores

Un supervisor es un proceso OTP que inicia y supervisa procesos hijos de acuerdo con sus especificaciones. Los supervisores pueden organizarse en árboles: la aplicación inicia un supervisor raíz, que a su vez puede iniciar otros supervisores y procesos de trabajo. Así se declara cómo se inician, se detienen y se reinician los componentes cuando fallan.

La estrategia determina qué hijos reiniciar ante una falla. Por ejemplo, `:one_for_one` reinicia solo al hijo que falló, mientras que `:one_for_all` reinicia todos los hijos. Un `DynamicSupervisor` permite iniciar hijos dinámicamente después de que el supervisor ya está en marcha; para hijos conocidos al iniciar, se declaran especificaciones en el supervisor habitual.

La supervisión no restaura automáticamente el estado que tenía un proceso antes de terminar. Si se reinicia un `GenServer` o un `Agent`, este se inicializa de nuevo; si el estado debe sobrevivir a una falla, hay que persistirlo o reconstruirlo explícitamente. Por eso, la política de reinicio y la recuperación del estado son decisiones distintas.

Más información: https://hexdocs.pm/elixir/Supervisor.html[Supervisor] y https://hexdocs.pm/elixir/DynamicSupervisor.html[DynamicSupervisor].
