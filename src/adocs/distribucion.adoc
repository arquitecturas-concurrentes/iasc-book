= Sistemas distribuidos

== Una definición

Un sistema distribuido reúne componentes independientes que colaboran mediante una red para ofrecer un servicio común. Una definición más precisa es:

[quote]
____
Un sistema distribuido es una colección de elementos informáticos autónomos que se comunican a través de una red, y que aparece a sus usuarios como un único sistema coherente.
____

La definición combina dos perspectivas. Por un lado, describe cómo está construido el sistema: sus componentes son autónomos y se comunican por una red. Por otro, indica qué experiencia busca ofrecer: que los usuarios perciban el servicio como una unidad. Cada parte señala una propiedad importante:

* *Elementos autónomos:* los nodos son computadoras o procesos que ejecutan de manera independiente. Pueden tener memoria y estado locales, y cada uno puede fallar sin que los demás fallen al mismo tiempo.
* *Se comunican a través de una red:* no comparten necesariamente memoria; coordinan su trabajo intercambiando mensajes. La red introduce demoras y puede perder o reordenar mensajes.
* *Un único sistema coherente para sus usuarios:* quienes usan la aplicación interactúan con un servicio o una interfaz común, aunque detrás haya varios componentes. Esta apariencia no significa que la distribución sea invisible en toda circunstancia: una interrupción puede afectar lo que el sistema puede responder.

Esta definición destaca la tensión central de la distribución: se busca coordinar componentes independientes como un conjunto, aunque cada nodo solo conoce los mensajes que recibió y el estado local que conserva.

== ¿Por qué distribuir un sistema?

Distribuir no es un objetivo en sí mismo. Puede ser útil cuando una sola máquina ya no alcanza, cuando hace falta atender usuarios desde distintas regiones, cuando se necesita continuar ante ciertas fallas o cuando distintas partes del dominio requieren ciclos de evolución independientes.

Algunas motivaciones frecuentes son:

* *Escalabilidad:* repartir carga de cómputo, almacenamiento o tráfico entre varios nodos.
* *Disponibilidad y tolerancia a fallas:* mantener algunas operaciones ante la caída de un componente, si hay redundancia y mecanismos para conmutar o recuperarse.
* *Cercanía geográfica:* atender a usuarios desde una región más próxima para reducir demoras.
* *Descomposición organizativa o funcional:* permitir que partes distintas del sistema tengan límites, responsabilidades o ciclos de despliegue propios.
* *Dominio naturalmente distribuido:* conectar participantes que ya están en lugares, redes u organizaciones diferentes.

Cada motivación trae decisiones y costos. La https://arquitecturas-concurrentes.github.io/iasc-book/replicacion/[replicación] puede aumentar la disponibilidad de lectura, pero obliga a decidir qué consistencia ofrecer. La https://arquitecturas-concurrentes.github.io/iasc-book/particionamiento/[partición de datos] reparte almacenamiento y trabajo, pero agrega enrutamiento y consultas que pueden cruzar nodos. Separar una aplicación en servicios puede permitir escalarlos por separado, pero agrega comunicación remota, contratos y operación. La distribución no garantiza automáticamente que el sistema sea más rápido, barato o confiable.

== Empezar de manera simple

Es frecuente empezar con una aplicación desplegada en una sola máquina o en pocas instancias coordinadas. Una arquitectura monolítica puede ser una buena opción inicial: simplifica el despliegue y permite que llamadas internas y cambios de estado ocurran dentro de un mismo proceso o base de datos.

[.center.iasc-image]
image::distribucion/image2.png[Ejemplo de una aplicación monolítica y su base de datos, width=500]

Conviene distinguir *monolito* de *una sola máquina*. Monolito describe cómo está organizada la aplicación; una aplicación monolítica puede ejecutarse en varias instancias detrás de un balanceador. A la inversa, una solución compuesta por servicios puede seguir dependiendo de un único servidor de base de datos. La organización del software y la topología de despliegue son decisiones relacionadas, pero no idénticas.

Al crecer el uso, pueden aparecer límites de CPU, memoria, almacenamiento, capacidad de la base de datos o velocidad de respuesta. Antes de distribuir, es útil medir qué recurso está saturado y cuál es el objetivo: aumentar capacidad, reducir latencia, mejorar la disponibilidad o separar responsabilidades. Distintos problemas requieren estrategias distintas.

== Lo que cambia al cruzar la red

Una llamada a otro nodo no se comporta como una llamada local. La respuesta puede tardar, perderse o llegar después de que quien espera haya vencido su timeout. Si se pierde la respuesta, el emisor puede no saber si la operación remota llegó a ejecutarse.

Además, cada nodo puede tener una vista distinta y temporal del estado. Copiar información no implica que todas las réplicas se actualicen al mismo tiempo, y detectar que un nodo no responde no permite saber con certeza si falló o si solo se interrumpió la comunicación con él.

Al diseñar una interacción distribuida conviene especificar:

* qué ocurre si la respuesta se demora o no llega;
* si es seguro reintentar la operación y cómo se reconocen duplicados;
* qué datos deben estar inmediatamente coordinados y cuáles pueden converger después;
* qué operaciones siguen disponibles ante una partición de red;
* cómo se recupera o reconcilia el estado al restablecerse la comunicación.

La sección sobre https://arquitecturas-concurrentes.github.io/iasc-book/mitos_distribucion/[las falacias de la computación distribuida] profundiza en supuestos que suelen quedar ocultos al pasar de llamadas locales a comunicación por red. Para la detección de actividad y el intercambio de información entre nodos, véase https://arquitecturas-concurrentes.github.io/iasc-book/heartbeat_gossip/[heartbeats y gossip]; para pensar la decisión bajo una partición, véase https://arquitecturas-concurrentes.github.io/iasc-book/cap/[CAP].

La coordinación cuando se pueden perder mensajes y la tolerancia a participantes que mienten se desarrollan en las páginas sobre https://arquitecturas-concurrentes.github.io/iasc-book/dos_generales/[los dos generales y el problema bizantino] y https://arquitecturas-concurrentes.github.io/iasc-book/protocolos_bft/[protocolos BFT].

== Escalabilidad: una decisión aparte

La escala horizontal es una motivación posible para distribuir, pero no es la única. Clonar una aplicación, dividirla en servicios y particionar sus datos son estrategias diferentes, que pueden combinarse y tienen costos propios.

Para profundizar en el escalado vertical y horizontal, el modelo de ejes X/Y/Z, los balanceadores y el manejo de sesiones, véase la página sobre https://arquitecturas-concurrentes.github.io/iasc-book/escalabilidad/[escalabilidad].
